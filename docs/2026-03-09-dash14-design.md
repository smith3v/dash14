# dash14 Design

## Overview

`dash14` is a local Go application that runs on the streaming laptop alongside OBS.
It maintains the current state of one volleyball match, renders an HTML overlay file
for OBS, and exposes match control through a Telegram bot.

The app supports exactly one active game per device. If another game needs to be
managed independently, `dash14` should be run on another device.

## Goals

- Render an OBS-ready HTML overlay from a template on the local filesystem
- Control the game from Telegram without a separate web UI
- Persist game state, teams, and users in a local SQLite database
- Support local YAML import of known teams and logos
- Keep match control restricted to configured Telegram admins
- Broadcast read-only updates to all subscribed bot users

## Non-Goals

- Multiple concurrent active games on one device
- Remote web administration UI
- Automatic match finish without admin confirmation
- Storing team logo binaries inside SQLite

## Runtime Modes

`dash14` has one binary and two startup paths:

- `dash14 --config config.yaml`
  Starts the normal runtime: config loading, logging, SQLite, Telegram bot, and
  overlay rendering.
- `dash14 --config config.yaml --import teams.yaml`
  Runs team import only and exits after the import completes.

There are no subcommands.

## Configuration

The app configuration uses YAML.

Expected config areas:

- Telegram bot token
- SQLite database path
- Planned overlay template path
- Live overlay template path
- Overlay output HTML path
- Managed logo directory path
- Logging level
- Logging file path

Config and logging structure should follow the approach already used in
`easy-recall-bot`, adapted to YAML instead of JSON.

## Team Import

Known teams are imported from a YAML file passed with `--import`.

Import behavior:

- Read a list of teams from YAML
- Map only known fields into the database
- Ignore unknown keys in team records
- Copy logo files into a managed local directory
- Store only metadata and relative logo paths in SQLite
- Update existing teams when they match on the explicit `key` field

Recommended minimum team fields:

- `key`
- `name`
- `short_name`
- `logo`
- `aliases`

Unknown fields must be ignored so the import format can grow later without
breaking older binaries.

The `key` field is required in YAML and is the only identifier used for upsert.
It must be explicitly provided by the operator and should be treated as stable.

## Logo Storage

Team logos should be stored as files on disk, not as blobs inside SQLite.

Rationale:

- Keeps the database smaller and easier to inspect
- Makes overlay template paths straightforward
- Simplifies replacing or updating logo assets
- Avoids rewriting large DB blobs for image updates

SQLite should store:

- relative logo path
- content type, if needed
- checksum, if needed for change detection

## Core Model

The app persists the following core entities:

- `teams`
- `games`
- `game_sets`
- `users`
- `app_state`

### teams

Stores known teams available for match selection.

Suggested fields:

- ID
- key
- name
- short_name
- logo_path
- created_at
- updated_at

### games

Stores one match and its aggregate state.

Suggested fields:

- ID
- home_team_id
- guest_team_id
- status (`planned`, `in_progress`, `finished`)
- current_set_number
- home_team_sets_won
- guest_team_sets_won
- overlay_home_team_on_left
- fifth_set_side_switch_applied
- current_admin_user_id
- created_at
- started_at
- finished_at

The match model tracks teams by identity. Overlay left/right placement is only a
representation concern and must not be used as the primary team mapping.

### game_sets

Stores per-set score data and the active set state.

Suggested fields:

- ID
- game_id
- set_number
- home_team_points
- guest_team_points
- winner_team_id
- status (`active`, `finished`)
- finished_at

This table supports both historical set results and the currently active set.

### users

Stores Telegram users known to the bot.

Suggested fields:

- telegram_user_id
- username
- subscribed
- is_admin
- created_at
- updated_at

Users remain in the database after `/stop` so future user-specific preferences can
be preserved.

### app_state

Stores singleton application state such as:

- current_game_id

## Match Rules

`dash14` manages a best-of-5 volleyball match.

Rules:

- At least 4 sets must be played
- If the set score is 2-2 after 4 sets, set 5 must be played
- If the set score is not 2-2 after 4 sets, the match becomes finish-eligible
- After set 5 is completed, the match becomes finish-eligible
- The app must not auto-finish the match
- When the match becomes finish-eligible, the bot must prompt the admin to
  confirm game finish

### Sets 1-4

- First to 25 points
- Must lead by at least 2 points

### Set 5

- First to 15 points
- Must lead by at least 2 points
- When either team reaches 8 points, the overlay sides switch automatically
- The automatic side switch must be applied at most once

### Set Completion

The app evaluates whether a set is finishable after every score change.

If the rule is met:

- The set is marked as ready to finish
- The bot asks the admin to confirm that the set is over
- The app does not auto-close the set

This prevents accidental scoring mistakes from immediately finalizing a set.

When the admin confirms set finish:

- The set result is stored as finished
- The winning team gains one set win
- If fewer than 4 sets have been completed, a new set is created at `0-0`
- If 4 sets are completed at `2-2`, set 5 is created at `0-0`
- The overlay sides swap automatically for the next set
- Otherwise, the bot prompts for game finish eligibility

## Game Lifecycle

The game lifecycle has three states:

- `planned`
- `in_progress`
- `finished`

`/plan` creates a new game in `planned` state. The match must not start
automatically after planning. The current game admin must explicitly start the game
before score tracking begins.

Only one non-finished game may exist at a time.

## Telegram Bot Behavior

The Telegram bot is the only control interface.

### Authorization

- Admin rights are stored in the `users` table via the `is_admin` flag
- Admin flags are managed manually in the database for now
- Only admins can mutate game state
- All other users are read-only subscribers
- Only one admin can control the current planned or active game at a time

### User Subscription

On `/start`:

- Create or update the user record
- Mark the user as subscribed
- Send a welcome message that clearly says the user is now subscribed to match
  updates by default

On `/stop`:

- Mark the user as unsubscribed
- Stop sending match updates to that user
- Keep the user record in the database

### Planning Flow

Admins can create a game with `/plan` only when there is no current non-finished
game.

`/plan` starts a wizard:

1. Ask for the home team
2. Search known teams with fuzzy matching
3. If 1 team matches, select it directly
4. If 2 to 8 teams match, show selectable options
5. If more than 8 teams match, ask the admin to refine the query
6. Ask for the guest team and repeat the same search flow
7. Create the game in `planned` state
8. Set the planning admin as the current game admin
9. Render the planned-game overlay immediately

The planning wizard must keep team identity separate from overlay left/right
placement. Team labels in the app are `home team` and `guest team`.

### Game Ownership

Each planned or active game has exactly one current game admin.

Rules:

- The admin who completes `/plan` becomes the current game admin automatically
- Only the current game admin can update the current game state
- Another admin may take over the current game
- Successful takeover must notify both the previous admin and the new admin
- After takeover, the previous admin loses write access for the current game
- A current or new control thread may invalidate the previous control thread

### Admin Actions

Admins need a simple control message with inline actions for:

- start a planned game
- increment or decrement either team score by 1
- confirm set finish
- confirm game finish
- reverse overlay sides manually if needed
- take over the current game

Admin actions should update the control message in place so the message always
reflects the current state.

### Game Control Commands

`/game` starts the current game management thread.

Behavior:

- If the caller is the current game admin, create a new control message and
  invalidate the previous active control thread
- If the caller is not the current game admin, reply with a message such as:
  `@username currently manages the game. Run /takeover if you would like to
  manage the game. The game control will transfer to you.`
- After takeover, the new admin must run `/game` to create a fresh control thread

The `/game` inline controls should make it visually obvious which team's score
will change. A simple baseline layout is separate button rows for the home team
and guest team, each with clear `-1` and `+1` actions.

Special-state inline actions should appear when relevant:

- `Start the game` for a planned game
- `Is set finished?` when the current set is finishable
- `Is game finished?` when a team has reached 3 set wins

The active control thread is allowed to evolve later with more buttons.

`/takeover` transfers current game administration to another admin.

On successful takeover:

- update `current_admin_user_id`
- notify the previous admin that control was transferred
- notify the new admin that they now manage the game
- invalidate the old control thread

### Broadcasts

Every state-changing admin action should broadcast a concise update to subscribed
users.

Example update:

`Set 4: Home Team 18-16 Guest Team | Sets 2-1`

## Overlay Rendering

The overlay is generated from HTML templates stored on disk.

Config should provide:

- planned template file path
- live template file path
- output HTML file path

The renderer should build a presentation-focused view model, including:

- home team name
- guest team name
- team logos
- current set points
- total sets won by each team
- current set number
- current overlay left/right placement
- game status

The overlay file should be written atomically so OBS never reads a partially
written file.

In `planned` state, the app should render the planned-game overlay.
In `in_progress` state, the app should render the live scoreboard overlay.

## Package Layout

Recommended package structure:

- `config`
  YAML loading and validation
- `logging`
  Logger construction and shared logging setup
- `storage`
  GORM models, migrations, and persistence access
- `game`
  Match rules, state transitions, and scoring logic
- `telegram`
  Bot handlers, admin UI, authorization, and broadcast flow
- `overlay`
  Template loading and HTML rendering
- `importer`
  YAML team import and logo file management

`game` contains the business rules for match and set state.
`storage` contains database access and persistence concerns.

## Startup Flow

Normal runtime startup:

1. Load YAML config
2. Initialize logging
3. Open SQLite database
4. Run schema migrations
5. Initialize storage services
6. Initialize Telegram bot
7. Load current active game, if any
8. Render overlay from current state
9. Start receiving Telegram updates

Import startup:

1. Load YAML config
2. Initialize logging
3. Open SQLite database
4. Run schema migrations
5. Import teams from YAML
6. Exit

## Error Handling

Startup should fail fast on:

- invalid config
- SQLite open failure
- migration failure
- invalid template setup
- import file parse failure

Runtime should be resilient on:

- Telegram broadcast failure to a specific user
- temporary Telegram API failure
- overlay write failure after a successful state update

Failures that occur after state mutation must be logged clearly and retried on the
next relevant event where possible.

## Testing Strategy

Prioritize deterministic unit tests and small integration tests.

Key test areas:

- YAML config parsing
- YAML team import with unknown-key tolerance
- logo copy and path persistence
- `/plan` wizard flow
- fuzzy team search result handling for 1, 2-8, and more than 8 matches
- scoring transitions for sets 1-4
- scoring transitions for set 5
- 5th-set automatic side switch at 8 points
- prevention of double side switch in set 5
- set-finish confirmation flow
- prompt-to-finish-game behavior at 3 sets won
- Telegram admin authorization checks
- single-current-admin ownership and takeover notifications
- subscriber lifecycle for `/start` and `/stop`
- overlay rendering from known game state
